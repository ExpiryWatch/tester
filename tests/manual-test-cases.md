# Ручные тест-кейсы проекта «Запасы»

Тест-кейсы для задач #495 и #730 в EduFlow. Все проверки пока имеют статус «Не выполнено».

## Перед прогоном

1. Запиши ветку или коммит, дату проверки и браузер, если тестируешь интерфейс.
2. Используй тестовую базу и отдельные тестовые записи.
3. Сверь с актуальным ТЗ правила для количества, сроков годности и сортировки записей без даты. Если правило ещё не согласовано, запиши фактическое поведение и отметь, что ожидаемый результат требует уточнения.

## Дополнительные проверки Backend 1

Все проверки выполняются на отдельной тестовой БД.
ID категорий и мест хранения получаем из API.
После ошибочных запросов повторно проверяем сохранённые данные.

| ID | Проверка | Шаги | Ожидаемый результат |
|---|---|---|---|
| TC21 | Полное обновление через PUT | Отправить PUT с полями name, quantity, unit, category_id, storage_location_id, purchase_date, expiry_date, comment. Затем отправить PUT без name. | Полный запрос — HTTP 200, все поля обновлены. Неполный запрос — HTTP 422, данные не изменяются. |
| TC22 | Частичное обновление через PATCH | Изменить только quantity. Затем отдельными запросами передать null в name, quantity и unit. | Корректный запрос — HTTP 200, остальные изменяемые поля сохраняются. Каждый запрос с null — HTTP 422, данные не изменяются. |
| TC23 | Количество при обновлении | Через PUT и PATCH отдельно установить quantity = 0 и quantity = -1. После каждого запроса перечитать продукт. | Все четыре запроса возвращают HTTP 422. Исходное количество сохраняется. |
| TC24 | Единицы измерения | Через POST, PUT и PATCH отдельно передать unit = "" и unit = "   ". Затем проверить unit = " кг " каждым методом. Выполнить POST без unit. | Пустые и пробельные значения — HTTP 422. При корректных запросах сохраняется "кг" без крайних пробелов. При POST без unit сохраняется "шт". Ошибочные запросы не изменяют данные. |
| TC25 | Категории и места хранения | Через POST, PUT и PATCH отдельно передать несуществующий category_id и несуществующий storage_location_id. | Все шесть запросов возвращают HTTP 422. Новые записи не создаются, существующие не изменяются. |
| TC26 | Статистика продуктов | На пустой тестовой БД запросить GET /stats/. Создать по одному продукту каждого статуса. Изменить количество одного продукта с 1 на 100. Изменить срок годности годного продукта на прошедшую дату. Удалить один просроченный продукт. Запрашивать статистику после каждого действия. | HTTP 200. Ответ содержит total, fresh, expiring_soon, expired, no_date. Сумма четырёх статусов равна total. После создания total = 4, каждый статус равен 1. Изменение количества не влияет на статистику. После изменения срока fresh = 0, expired = 2. После удаления total = 3, expired = 1. |
| TC27 | Пагинация и комбинированные фильтры | Создать не менее 7 позиций с разными названиями. Сравнить полный список с GET /inventory/?limit=3&offset=3. Проверить сочетание category_id, status=expired, sort=expiry и order=asc на нескольких подходящих продуктах. Отдельно передать limit=0 и offset=-1. | Корректные запросы — HTTP 200. Пагинация возвращает позиции с 4-й по 6-ю. Фильтры работают одновременно, даты отсортированы по возрастанию. Некорректные параметры — HTTP 422. |
| TC28 | Сохранение просроченного продукта | Через POST создать продукт с purchase_date = T - 1 день и expiry_date = T - 2 дня. Перечитать продукт по ID. | HTTP 201, продукт сохранён. Статус expired, days_left = -2. Ошибка HTTP 500 не возникает. |

## Шаблон баг-репорта

- **Заголовок** — что ломается и при каком действии.
- **Связанный тест-кейс** — TC__.
- **Версия и среда** — коммит, браузер, дата и тестовые данные.
- **Шаги воспроизведения** — действия по порядку.
- **Ожидаемый результат** — что должно произойти.
- **Фактический результат** — что произошло.
- **Приоритет** — какой пользовательский сценарий затронут и насколько сильно.
- **Подтверждение** — скриншот, лог или ответ API, если есть.
- **Повторная проверка** — версия с исправлением и результат повторного прогона.
